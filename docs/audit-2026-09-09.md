# Baton audit, 9 September 2026

The reported installation failure is reproducible. The latest published release is [v0.1.0](https://github.com/danieldunderfelt/baton/releases/tag/v0.1.0), from 27 August. Its checksum-verified macOS binary rejects `baton install --user` and has no `baton update` command. Both commands were added later, while the README on `main` already described them. The source and published package also both reported version 0.1.0, hiding the difference.

This audit started at `1fd9c19`. It covered the CLI, host registration, installers and releases, adapters, execution and failover, persistence, routing, ratings and duels, MCP, the sharing service, website and documentation. Opus reviewed the core and website independently through Baton, then reviewed the fixes. A separate review covered the CLI and release changes. Delegated findings were checked against files and runnable reproductions before adoption.

## Fixed

| Area | Defect and resulting behavior |
| --- | --- |
| Releases | Source is versioned 0.2.0, and MCP uses the same package version. CI exercises the compiled binary from an unrelated directory with an empty PATH and disposable home. A release tag must match the package version. |
| Installation recovery | The README explains the v0.1.0 mismatch, rebuilding from source, PATH precedence and restarting agent sessions. The curl installer refuses an obsolete latest release before overwriting an existing install. |
| Download consistency | The shell installer resolves `latest` once, then downloads the binary and checksum from that exact tag. It runs the staged binary before replacing the installed copy and reports its version and path. |
| Updates | A newer local build is not downgraded to an older published release. Unique staging directories avoid collisions, symlink targets are updated without replacing the links, and a failed checksum or version probe preserves the installed binary. Source updates use the lockfile. |
| Host registration | Corrected the alternate Claude config location. Source registrations use the current Bun executable and absolute entrypoint rather than a stale compiled file. OpenCode registration supports JSONC and `OPENCODE_CONFIG`. |
| Config preservation | Registration preserves existing file permissions and symlinks, edits JSONC without discarding comments, rejects invalid MCP containers, and verifies that TOML changes leave unrelated settings intact. Damaged instruction markers are rejected before changing MCP configuration. |
| CLI behavior | Help requests are handled before side effects, including `mcp --help`. Unknown commands, extra arguments on argument-free commands, missing flag values and assignments to boolean flags produce usage errors. `status` includes the executable and version. |
| Database retention | Pruning a graded run used to fail a foreign-key constraint during database startup. Grades for evicted runs are now removed in the same transaction; aggregate rating evidence remains intact. |
| Codex | Restricted resume flags now precede the `resume` subcommand. The `edits` invocation uses `--approve-for-me`, which selects workspace-write and conflicts with an additional `--sandbox` in Codex 0.153.4. Closed-stdin probes verify argument parsing without starting a model turn. |
| Failover | Work-start markers are remembered across the entire output stream, including chunk boundaries. A long diagnostic log can no longer erase evidence of work and cause an unsafe retry on another account. |
| Output extraction | JSON envelopes have a separate bounded capture from the diagnostic tail. Large valid responses retain their answer and session; responses beyond 16 MiB fail explicitly instead of being parsed from a truncated tail. |
| Provider cooldowns | An OpenCode provider refusal no longer parks unrelated providers. The database upgrade preserves other apps' cooldowns and drops old OpenCode cooldowns that have no provider attribution. Pool output names cooling providers. |
| Model listing | Listings use real configured pool members. Quota counts are computed once per instance rather than once per model; provider-specific cooldowns still appear beside the relevant routes. |
| OAuth | Login redirects allow Astro to append its state cookie. Return paths are validated using browser URL parsing, closing control-character and backslash redirect bypasses. |
| Device authentication | Token creation and device-code consumption are atomic. A failed insert leaves the approved code redeemable; concurrent polls mint only one token. |
| Sharing | Concurrent first sign-ins and profile publications use atomic upserts. CLI and website share one code alphabet, formatter and normalizer. Malformed escaped share links return a normal input error. Device labels default to `cli` rather than the hostname. |
| HTTP input | Request limits count streamed UTF-8 bytes and cancel oversized bodies. Device endpoints reject null, arrays and primitive JSON with a client error. |
| Website | Missing or revoked shares render the shared not-found component with HTTP 404. Dynamic routes and static assets receive frame protection and other response headers. Production checks verify the built Worker and assets together. |
| Cleanup | Removed stale PLAN.md references and phase narration, centralized the repeated transaction helper, and corrected documentation that described observed headroom as actual subscription quota. Caller installation support is distinguished from callee support. |

## Validation

Final local results: 783 CLI tests passed, 13 optional live tests skipped, and 12 website tests passed. Root TypeScript checks passed. Astro reported zero errors and warnings, with six non-blocking hints. All four binaries compiled; the native release artifact and the built website passed their smoke checks.

Run the same checks locally with:

```sh
bun install --frozen-lockfile
bun run check
bun run build
bun run test
bun run check:release
bun run build:all
cd site
bun install --frozen-lockfile
bun run check
bun test
bun run build
bun run check:production
```

The release check registers all four supported caller hosts using the actual compiled binary. The shell installer and updater tests use local release fixtures and verify that failure preserves the prior installation. Regression tests cover old-schema upgrades, graded-run retention, provider isolation, long output and stream boundaries. Website tests use local workerd D1 for concurrency and transaction rollback, followed by HTTP checks against the production build.

The original suite passed before changes, so a green baseline alone did not establish that the documented installation worked. The added artifact and production checks address that gap.

## Limits and release status

- The fixes are local source changes until v0.2.0 is published. The default remote installer still points to the published v0.1.0 release. Source installation is the documented recovery path in the meantime.
- macOS and Linux binaries compile for both arm64 and x64. Local execution checks cover the native macOS arm64 artifact. The release workflow now tests all four downloaded artifacts on matching [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) before publication. Those remote jobs have not run as part of this local audit.
- Tests that start real model turns remain opt-in. This audit used Baton delegations on installed Claude Code and Codex, plus quota-free Codex argument probes; it did not run the entire live model matrix.
- The website checks use local D1 and verify the start of OAuth without contacting GitHub. They do not complete a real OAuth login or deploy to Cloudflare.
- The sharing service still has no per-account total storage cap. Adding a limit requires choosing a product policy; the request-size bound and authentication do not provide that limit.
- Reliability observations remain separate from answer-quality ratings. This audit did not invent a new routing penalty for failed executions.
